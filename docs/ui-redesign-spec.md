# CLO-V iOS: UI Redesign Spec (for Claude Code)

Source: 10 hand-drawn sketches. Reviewed against the real project at `~/Desktop/CLOV-iOS` on 2026-11-15 (HEAD `4ebca28`, plus 12 uncommitted modified files). Section 2 is the audit result. Everything marked "verified" was read from the repo; anything I did not read is called out.

The app already exists and is well past prototype stage. This is a **redesign of an existing app**, not a build from scratch. Reuse what is there, change what the sketches change, and do not remove features the sketches do not mention.

## 0. How to work with this doc

1. **Before any code:** create a branch (`feat/ui-redesign`) and commit or stash the 12 uncommitted files. Several of them (`MainTabView`, `AccountView`, `FeedView`, `SwipeFitCheckPage`, `ReelVoteModel`) are the files this redesign touches. Confirm the existing unit and UI tests pass, and record that baseline.
2. **The audit in section 2 is already done.** Spot-check it against the code rather than redoing it. Correct this doc where it is wrong and tell me what you changed.
3. **Build in the phases in section 8, one at a time.** Stop after each phase with: what changed, what you assumed, what to test by hand. Do not start the next phase until I say go.
4. **Additive changes only** to the database. No dropped tables or columns. Old posts must keep rendering.
5. **Match the sketches for layout and behavior, but use the app's existing design system** (`Theme`, existing components). The sketches are wireframes, not final art.
6. **Ambiguous sketch?** Use the default in section 3 and flag it. Only stop and ask when a choice is expensive to reverse.
7. Add a short `CLAUDE.md` at the repo root pointing to this doc. There is none today (`project.yml` mentions an "original CLAUDE.md" that is not in the repo).

## 1. Project facts to respect

**Stack (verified)**
- SwiftUI, iOS 17.0 deployment target, iPhone only, `supabase-swift` 2.x.
- The Xcode project is generated by **XcodeGen** from `project.yml`. Add files by placing them under `CLOV/Sources/` and running `xcodegen generate`. Do not hand-edit `project.pbxproj`.
- Code layout: `Sources/{App,Components,Models,Networking,Screens}`. Networking uses `API.swift` plus `API+<Area>.swift` extensions. New endpoints go in a new or existing `API+*.swift`.
- Existing helpers to reuse, not rebuild: `Theme` and `ThemePalette` (user-selectable palettes), `FloatingTabBar`, `FlowLayout` (wrapping chips), `ChipToggle` / `ChipButtonStyle`, `FeedIconButton`, `Haptics`, `ImageCache`, `PhotoCropView`, `PhotoZoomView`, `SkeletonViews`, `AsyncStateView`, `EmptyStateView`, `ShareLinkButton`, `ResultShareCard`, `InviteCodeCapsule`, `motionSafeAnimation`, `friendlyMessage(for:)`.
- Accessibility is taken seriously here: Dynamic Type caps, Reduce Motion handling, VoiceOver labels, and accessibility identifiers that UI tests depend on. New UI must follow the same pattern, and **hold-to-vote needs an accessible alternative** (an accessibility action or a button).

**Backend (verified)**
- Supabase project. Tables that already exist: `profiles`, `fit_checks`, `fit_check_photos`, `fit_check_votes`, `fit_check_comments`, `groups`, `group_members`, `notifications`, `profile_follows`, `friendships`, `friend_requests`, `blocked_users`, `content_reports`, `feed_events`, `wardrobe_items`, `device_tokens`, `wardrobe_tryon_jobs`, `catalog_items`.
- The migrations folder is incomplete by design (see `supabase/migrations/README.md`). The live schema snapshot is `supabase/baseline/remote_schema_2026-11-03.sql`. Several recent migrations are **untracked in git**, so do not assume which ones are applied to the live project. Run `supabase migration list` first, as the README says.
- Migration conventions in the existing files: filename `YYYYMMDDNNNNNN_name.sql` (latest is `20261106000100`), a matching file in `supabase/rollback/`, `security definer` functions use `set search_path = ''`, `revoke ... from public, anon` then `grant ... to authenticated`, and visibility rules repeat the block check (`is_blocked_pair`) and group check (`is_group_member`).
- **`fit_checks.vote_prompt` is not in the baseline snapshot.** The client reads it in a separate query and treats it as "an optional enhancement" for older deployments (`API.swift`). Check whether the live database has it. If it does not, D1 below needs a small migration.
- **Audience is only half wired.** The Create screen offers Everyone / Friends / A group / Only me, but `API.createFitCheck` deliberately rejects Friends and Only me, because the live `create_fit_check_draft` RPC only understands public versus group (`is_public = group_id is null`). Today, picking Friends or Only me fails at post time.
- Posting is a two-step server flow: `create_fit_check_draft` then `publish_fit_check`. A recent commit fixed parameter mismatches on these RPCs, so **read their current signatures before changing them**, and keep new parameters optional with defaults.

**Tests (verified):** 17 unit test files and 6 UI test files. UI tests use accessibility identifiers `feedTab`, `searchTab`, `activityTab`, `accountTab`, `tabPlusButton`. Changing the tab bar will break `PlusButtonUITests`, `DeepLinkUITests` and others. Update them in the same phase. `SwipeVoteGestureTests` will need replacing in the vote-screen phase.

**Running on a device without a paid Apple Developer account**
- `CLOV.entitlements` declares Push Notifications (`aps-environment`) and Sign in with Apple. A free personal team cannot sign either capability, so on-device builds will likely fail to sign. The Simulator is unaffected. I have not built this, so treat it as likely rather than confirmed.
- Suggested fix in Phase 0: add a Debug-only entitlements file with neither capability and point the Debug config at it in `project.yml`. On a device build, Sign in with Apple and push will not work, but email sign-in and Google (web auth session) will. Release keeps the real entitlements.
- `DEVELOPMENT_TEAM` is empty and `CLOVShareBaseURL` is empty in `project.yml`. See section 3, D12.

**Out of scope for this pass:** direct messaging, Crowned Voters, credits and monetization, expert/partner product links, the pitch deck's `CLO-Z` wardrobe percentages. The pitch deck PDF is the earlier concept; **where it disagrees with the sketches, the sketches win.**

```sql

alter table public.fit_checks add column if not exists tags text[] not null default '{}';

create table public.fit_check_bookmarks (
```

- **RLS:** likes and bookmarks are writable only as the current user and readable only where the parent Fit-Check is visible to the caller (reuse the same visibility and block rules as `get_fit_check_results`). A bookmarks row is readable only by its owner.
- `like_count`: maintain it with a trigger, the same way `vote_count` is maintained. Account deletion (`delete-account` function and the deletion RPC) must also remove the new rows; check the cascade covers them.
- **RPCs:** extend `create_fit_check_draft` / `publish_fit_check` (or the photo insert) to accept per-photo description and tags, and post-level tags. New parameters optional with defaults, so the old app version keeps working.
- **Live results (Phase 6):** add an RPC that returns the live per-photo tally only if the caller has voted or is the creator, then tighten the `fit_check_votes` SELECT policy to the voter's own row plus the creator. Remove the `fit_check_votes` embed from the feed select, and have the client read counts from the RPC. Look at every call site of `fitCheckVotes` first (`FeedItemDTO`, `ReelVoteModel`, `FitCheckCardView`, `VotingPhotoGridView`). Coordinate with me before applying this to the live project.

## 7. Interaction details

- **Auto-rotation:** one timer per visible card. Set a per-card `userInteracted` flag on any touch, which cancels the timer permanently. Stop it entirely under Reduce Motion.
- **Hold to vote:** `LongPressGesture` with a progress state and `.sensoryFeedback`. Prevent double votes locally; the unique vote constraint is the real guard. The existing `API.castVote` handles `alreadyVoted`.
- **Count reveal:** blur radius and opacity bound to `hasVoted || isCreator || ended`, animated.
- **Comment sheet:** `presentationDetents`, keyboard-safe input row.
- **Masonry (Explore, Profile):** two columns, heights from aspect ratio. A custom `Layout` or two lazy stacks. Build one shared component.
- **Scroll-aware member row (Group Feed):** track scroll direction and animate the row in and out.
- **New shared components to build once:** photo carousel with optional auto-advance, hold-to-vote gesture, masonry grid, like button, bookmark button.
